<a id="adr-001"></a>
### ADR-001 · Turborepo + pnpm monorepo — Accepted

- **Context:** The API, web and shared contracts (GraphQL schema, realtime event types, ordering algorithm) change together.
- **Decision:** One repo. pnpm workspaces + Turborepo for the task graph and caching. Packages under `@tb/*`.
- **Consequences:** Atomic cross-stack changes, one CI. Docker builds need `turbo prune` to stay small.

<a id="adr-002"></a>
### ADR-002 · Modular monolith with DDD bounded contexts — Accepted

- **Context:** The domain is rich but the team is small. Microservices would add network, deployment and consistency costs with no payoff yet.
- **Decision:** One NestJS codebase with one module per bounded context and strict layering ([04 §4](./04-architecture.md#4-backend-nestjs--ddd)). Two entrypoints: `api` (HTTP/GraphQL/SSE) and `worker` (relay, consumers, cron).
- **Consequences:** Contexts can later be extracted into services along the event boundaries already in place. Import-boundary linting is mandatory to keep the modules honest.

<a id="adr-003"></a>
### ADR-003 · Next.js is the BFF, the API is private — Accepted

- **Context:** The requirement is Next.js as BFF communicating by GraphQL.
- **Decision:** The browser talks only to Next.js (pages, Server Actions, `/api/*` route handlers). Next.js calls the API over GraphQL on the private network. The only bypass is presigned object-storage URLs.
- **Consequences:** Tokens never reach browser JS. One origin, so no CORS for the app. Costs an extra hop, and the BFF must proxy streams (SSE) correctly.

<a id="adr-004"></a>
### ADR-004 · API owns auth, BFF holds tokens in httpOnly cookies — Accepted

- **Context:** Identity is a bounded context with its own rules (verification, lockout, sessions). Putting auth in Next.js (Auth.js) would split identity across two codebases.
- **Decision:** The API issues a 15-minute access JWT (`sub`, `sid`) and an opaque 30-day refresh token (rotated, hashed at rest, 10 s grace window, reuse detection). The BFF stores both in httpOnly cookies and refreshes in `proxy.ts`. A revoked-sid cache marker gives immediate revocation.
- **Alternatives:** Auth.js in Next.js (rejected: duplicates the identity model). Opaque server sessions only (viable, but needs a session lookup on every API call).
- **Consequences:** Stateless API auth on the hot path. Needs careful cookie and refresh handling in the BFF ([Sequence 03](./diagrams/sequence/03-silent-session-refresh.md)).

<a id="adr-005"></a>
### ADR-005 · Realtime via SSE through the BFF, RabbitMQ as backplane — Accepted

- **Context:** "WebSocket or SSE for realtime updates of ticket movement." Updates are **server → client**. Client → server already goes through GraphQL mutations.
- **Decision:** **SSE**, one stream per tab (user channel + current board channel), proxied by a Next.js route handler. Each API instance consumes its own exclusive RabbitMQ queue bound to `tb.events` and pushes to its local connections.
- **Why not WebSocket:** Next.js route handlers can't upgrade to WebSocket, so WS would need a separate public gateway and break the BFF-only rule. A WS gateway would also need its own auth and reconnect logic. SSE gives automatic reconnect, works over HTTP/2, and authenticates with the same cookies.
- **Why RabbitMQ and not cache pub/sub:** Memcached has no pub/sub, and the cache must stay swappable ([ADR-008](#adr-008)).
- **Consequences:** Every hop must disable buffering. Presence and typing indicators (P2+) would also need a client → server channel. If those become core, add a WS gateway behind the same edge as a new ADR.

<a id="adr-006"></a>
### ADR-006 · Fractional-index string keys for ordering — Accepted

- **Context:** Lists, tickets, checklists and items are reordered constantly and concurrently. Integer positions require renumbering siblings. Trello-style floats eventually lose precision.
- **Decision:** `position text COLLATE "C"` with keys from the `fractional-indexing` algorithm, shared by client and server through `packages/ordering`. The API takes **neighbour ids**, not positions. Writers are serialised per list with a row lock.
- **Consequences:** One-row updates. Keys grow slowly and a rebalance job handles pathological cases. Clients must sort with byte comparison.

<a id="adr-007"></a>
### ADR-007 · Transactional outbox + RabbitMQ — Accepted

- **Context:** Publishing to RabbitMQ inside a request either loses events (crash after commit) or publishes phantom events (crash before commit).
- **Decision:** Events are inserted into `outbox_events` in the same transaction. A single-leader relay (advisory lock, woken by LISTEN/NOTIFY) publishes them with confirms. Consumers dedupe via `processed_messages`. Retries use TTL queues, then a DLQ.
- **Consequences:** At-least-once delivery with exactly-once effects. A few ms of extra latency. The relay needs a direct (non-pooled) DB connection.

<a id="adr-008"></a>
### ADR-008 · Cache Facade with pluggable drivers — Accepted

- **Context:** Requirement: support Redis or Valkey, and Memcached, through a Facade.
- **Decision:** `CacheFacade` (cache-aside `remember` with single-flight, tag versions, rate limiting, best-effort locks) on a minimal `CacheDriver` contract. A RESP driver serves Redis and Valkey, plus Memcached and memory drivers. Selected by `CACHE_DRIVER`. **Fail-open.**
- **Consequences:** No Redis-only features (pub/sub, Lua, streams) anywhere in the app. Realtime and queues use RabbitMQ instead. Correctness never depends on the cache.

<a id="adr-009"></a>
### ADR-009 · Presigned URLs for RustFS — Accepted

- **Context:** Streaming files through Node processes wastes memory and bandwidth.
- **Decision:** The browser uploads and downloads directly with short-lived presigned URLs, after an API permission check. There are two S3 clients: internal for operations, public for signing.
- **Open risk:** RustFS CORS and bucket-policy support must be verified on the pinned version. Fallback: BFF streaming upload route.

<a id="adr-010"></a>
### ADR-010 · UUIDv7, app-generated — Accepted

- **Decision:** All primary keys are UUIDv7 generated in the domain layer. Clients supply ids for creates, which makes them idempotent and removes temp-id swapping. Human-facing ids are `short_id` (base62) and the per-board ticket `number`.
- **Consequences:** Time-ordered ids double as keyset pagination cursors and chronological sort keys.

<a id="adr-011"></a>
### ADR-011 · Activity log written in the command transaction — Accepted

- **Context:** The activity feed must match the board state immediately ("moved from To Do to Doing" right after the move).
- **Decision:** An in-process `ActivityRecorder` maps domain events to `activities` rows inside the command's transaction. Notifications, emails, previews and realtime stay async.
- **Consequences:** It's a deliberate, documented cross-context write (Board → Collaboration's table) through a published interface. Simpler than an eventually consistent projection.

<a id="adr-012"></a>
### ADR-012 · Optimistic concurrency — Accepted

- **Decision:** Every aggregate row has a `version`. Only title and description edits require `expectedVersion` from the client (lost-update risk). Commutative commands retry server-side on version races. Realtime events carry `version` so clients drop stale ones.

<a id="adr-013"></a>
### ADR-013 · `text + CHECK` instead of PostgreSQL enums — Accepted

- **Decision:** Status and role columns are `text` with `CHECK (col IN (...))`. Adding values is a constraint swap inside a normal migration. Enum types are generated in TypeScript from a single source.

<a id="adr-014"></a>
### ADR-014 · Secret tokens minted by the worker — Accepted

- **Decision:** Verification, reset and invitation tokens are generated by the worker that sends the email. Only their SHA-256 hash is stored. Events carry ids, never raw tokens, so neither the outbox nor RabbitMQ ever holds a usable secret.

<a id="adr-015"></a>
### ADR-015 · "Ticket" is the domain term for "card" — Accepted

- **Decision:** The product is a *ticket board*. Code, schema and API use **Ticket** (`tickets`, `moveTicket`). The visual tile component is `TicketCard`. The mapping to Trello terms is in [01 §6](./01-trello-analysis.md#6-terminology-mapping-trello--ticket-board).

<a id="adr-016"></a>
### ADR-016 · TypeORM, with persistence entities kept out of the domain — Accepted

- **Context:** TypeORM is the preferred ORM. Its decorators normally sit on the classes the domain layer must keep pure ([ADR-002](#adr-002)).
- **Decision:** Use TypeORM as a persistence adapter only. `*.orm-entity.ts` classes live in `infrastructure/persistence/`, and explicit mappers convert them to and from aggregates. `synchronize` stays off, and migrations run raw SQL. Version checks are explicit `UPDATE … WHERE version = :v`, because `save()` doesn't compare versions. The outbox relay uses a raw `pg` client for `LISTEN` and its advisory lock.
- **Consequences:** Each persisted aggregate needs an ORM entity and a mapper, which adds boilerplate. Mapping rules are in [06 §9](./06-database.md#9-typeorm-mapping).

<a id="adr-017"></a>
### ADR-017 · Tailwind + shadcn/ui in a shared `@tb/ui` package — Accepted

- **Decision:** `packages/ui` holds the shadcn/ui components, the Tailwind theme and the global CSS, using shadcn's monorepo setup. `apps/web` imports from `@tb/ui` and compiles it through `transpilePackages`.
- **Rules:** `@tb/ui` has no data fetching, GraphQL or `next-intl`. Labels arrive as props. Domain components such as `TicketCard` stay in `apps/web/src/features`.
- **Consequences:** A second app could reuse the design system. Adding a shadcn component means running the CLI against the package, not the app.

<a id="adr-018"></a>
### ADR-018 · dnd-kit for drag and drop — Accepted

- **Decision:** dnd-kit, with one `DndContext` per board, one `SortableContext` per list and a `DragOverlay` for the dragged ticket. The keyboard sensor covers keyboard dragging.
- **Consequences:** Replaces the earlier Pragmatic drag and drop recommendation. Large lists need memoised `TicketCard`s to keep dragging smooth. State mapping is in [State 14](./diagrams/state/14-ticket-drag-ui.md).

<a id="adr-019"></a>
### ADR-019 · One set of codegen documents, server and browser GraphQL clients — Accepted

- **Decision:** `graphql-codegen` generates typed documents from `apps/api/schema.gql`. Two thin clients share them:
  - `src/lib/graphql/server.ts` is `server-only` and calls the API directly. Server Components, Server Actions and route handlers use it.
  - `src/lib/graphql/browser.ts` posts to `/api/graphql`, and TanStack Query uses it for client components.
- **Why TanStack Query stays:** SSE reducers patch the board state, so a normalised GraphQL cache would add little.
- **Consequences:** The same query can prefetch on the server and hydrate in the browser, fully typed. The `server-only` import stops the server client from reaching the browser bundle.

<a id="adr-020"></a>
### ADR-020 · Jest for the API and packages, Playwright for the web app — Accepted, Jest part superseded by ADR-028

- **Decision:** The API uses NestJS's default test setup: Jest, `@nestjs/testing` and Supertest, plus Testcontainers for infrastructure tests. Shared packages use Jest too. The web app uses Playwright.
- **Consequences:** Replaces the earlier Vitest recommendation. The web app has no separate component-test layer, so UI behaviour is covered through Playwright.

<a id="adr-021"></a>
### ADR-021 · Outbound messages behind a `DeliveryFacade` — Accepted, SMS part superseded by ADR-025

- **Context:** Providers should be swappable, and sending should be testable in Docker.
- **Decision:** `DeliveryFacade` follows the cache pattern: a small contract with drivers selected by `EMAIL_DRIVER` and `SMS_DRIVER`. Only the worker calls it. Email ships in the MVP with `smtp` (Mailpit locally) and `memory`. The SMS contract exists, but its default driver is `none`.
- **Why no SNS emulator:** LocalStack has required an auth token since 2026.03.0. A dev `smtp-sink` driver can show SMS in Mailpit instead, with no extra container.
- **Consequences:** Adding a provider is one driver. Details are in [10 §11](./10-infrastructure.md#11-delivery-facade).

<a id="adr-022"></a>
### ADR-022 · Step-by-step scope: no public boards or OAuth in the MVP — Accepted

- **Decision:** Board visibility is `private` or `workspace`, and every board needs a signed-in user. Login starts with email and password. Public boards (BRD-19) and OAuth (ACC-11) are unscheduled.
- **Consequences:** No anonymous read paths and no `PUBLIC_VIEWER` role. Workspace `visibility` is dropped. Adding public boards later is a `CHECK` swap ([ADR-013](#adr-013)) plus anonymous-access work.

<a id="adr-023"></a>
### ADR-023 · i18n: cookie on the web, `Accept-Language` to the API — Accepted

- **Decision:**
  - The web app uses `next-intl` with a `tb_locale` cookie and no locale in the URL.
  - The BFF sends the resolved locale to the API in `Accept-Language`, and `nestjs-i18n` translates errors and validation messages.
  - The worker uses the recipient's `users.locale` for emails.
  - The domain only produces codes and data.
- **Why cookie, not path:** With no public pages there's no per-language SEO to gain. Shared links open in the reader's language, and the intercepted ticket modal route stays simple.
- **Consequences:** Details are in [12 · Internationalisation](./12-internationalisation.md).

<a id="adr-024"></a>
### ADR-024 · Docker first, Kubernetes-ready, no hosting yet — Accepted

- **Decision:** No hosting target for now. Services run on Docker Compose, and stay ready for Kubernetes through stateless containers, health endpoints, graceful `SIGTERM` handling and migrations as a one-shot job ([10 §1](./10-infrastructure.md#1-environments)).
- **Consequences:** No staging, production or manifests yet.

<a id="adr-025"></a>
### ADR-025 · Email is the only delivery channel for now — Accepted

- **Context:** [ADR-021](#adr-021) left room for SMS, but no feature needs it.
- **Decision:** This supersedes the SMS part of ADR-021. `DeliveryFacade` has `sendEmail` only. `sendSms`, `SMS_DRIVER` and all SMS drivers are out of the design. The facade and its email drivers stay as decided.
- **Consequences:** No unused code or config to maintain. Adding SMS later takes a feature ID, phone numbers on `users`, a `sendSms` method and an `SmsDriver`. Existing `sendEmail` callers don't change.

<a id="adr-026"></a>
### ADR-026 · SSE stays behind the BFF, with its own process as the scale path — Accepted

- **Context:** [ADR-005](#adr-005) sends streams through the BFF. Could the browser use the BFF for HTTP but connect straight to the API, or to an SSE service, for streams?
- **Decision:** The MVP keeps browser → BFF → `api`. The browser never connects to the API directly. The `realtime` module stays self-contained, so it can move to its own process without changes in other contexts.
- **Why not direct to the API:**
  - The API would have to be public, which exposes all of GraphQL, not just the streams ([ADR-003](#adr-003)).
  - A second origin needs CORS and cross-site cookies. `EventSource` can't set an `Authorization` header, so the token would have to travel in a cookie or the URL.
  - `proxy.ts` wouldn't run on reconnect. An expired token would return 401, and `EventSource` doesn't retry after that.
- **Why not the existing `worker`:** It scales on queue depth, while streams scale on open connections. A worker deploy also shouldn't drop every stream.
- **Scale path:** Each later step needs its own ADR, written when its trigger appears ([diagram](./diagrams/architecture/12-realtime-scale-path.md)).

  | Step | Path | Move when |
  |---|---|---|
  | 1 · MVP | Browser → BFF → `api` | Now |
  | 2 · Own process | Browser → BFF → `realtime`, a third entrypoint (`src/realtime.ts`) | Streams start to drive `api` scaling, or `api` deploys drop too many streams |
  | 3 · Edge route | Browser → edge → `realtime`, for `/api/realtime` only | Streams start to drive `web` scaling, or `web` deploys cause reconnect bursts |

- **What step 3 costs:** It stays on one origin, so there's no CORS. But `realtime` must read the session cookie itself, and the client must refresh the session before it reconnects, because `proxy.ts` no longer runs on that route. It also makes `realtime` reachable from the edge, so it needs to supersede ADR-003 for that one route.
- **Consequences:** Each open tab holds two sockets on `web` in the MVP, one to the browser and one to the API. Deploying `web` or `api` drops streams, and clients recover by reconnecting and refetching ([Sequence 19](./diagrams/sequence/19-sse-connection-lifecycle.md)).

<a id="adr-027"></a>
### ADR-027 · File uploads: presigned PUT between two GraphQL mutations — Accepted

- **Context:** [ADR-009](#adr-009) moves file bytes off Node. This ADR sets how GraphQL, NestJS and Next.js fit around that.
- **Decision:**
  - GraphQL carries metadata, never bytes. The flow is `requestAttachmentUpload`, a browser PUT to RustFS, then `confirmAttachmentUpload`.
  - The client supplies the attachment id. Repeating the request with the same id returns a fresh URL, which also covers expired URLs.
  - Confirm verifies the object with HEAD and accepts nothing else from the client.
  - Avatars and logos use `requestImageUpload` and `confirmImageUpload`. They upload to a private `incoming/` key, and the worker re-encodes them into `tb-public`.
  - Object keys are ids only, which fixes the earlier `safeName` key that conflicted with rule 13.
- **Why not GraphQL multipart:**
  - Next.js buffers request bodies when `proxy.ts` is used, and keeps only the first 10 MB by default without failing the request, so a 25 MB file would arrive cut off.
  - `/api/graphql` accepts only JSON and persisted operations.
  - Every byte would cross both Next.js and NestJS.
- **Why PUT rather than presigned POST:** RustFS lists presigned PUT as tested. Its matrix doesn't cover POST policy conditions such as `content-length-range`.
- **Why not S3 multipart yet:** The limit is 25 MB, and S3's guidance starts at 100 MB. [13 §11](./13-file-uploads.md#11-later-larger-files) sketches the later design.
- **Consequences:** Three calls per upload, and `pending` rows need GC. A file uploaded but never confirmed is lost after an hour. Avatar and logo results arrive by SSE rather than in the mutation response. Details are in [13 · File uploads](./13-file-uploads.md).

<a id="adr-028"></a>
### ADR-028 · Vitest + Supertest for the API and packages — Accepted

- **Context:** The NestJS 12 starter ships Vitest and Supertest instead of Jest.
- **Decision:** This supersedes the Jest part of [ADR-020](#adr-020). The API and the shared packages use Vitest. The API also uses `@nestjs/testing`, Supertest for HTTP and GraphQL, and Testcontainers for infrastructure tests. The web app keeps Playwright.
- **Consequences:** The test layers don't change: pure domain tests, application tests with in-memory repositories, Testcontainers for infrastructure and Supertest at the edge. The exact Vitest setup is settled during implementation.

<a id="adr-029"></a>
### ADR-029 · oxlint for every workspace — Accepted

- **Context:** The NestJS 12 starter lints with oxlint instead of ESLint. [ADR-002](#adr-002) makes import-boundary linting mandatory.
- **Decision:** `apps/api`, `apps/web` and `packages/*` all lint with oxlint. The import boundaries in [04 §4.2](./04-architecture.md#42-layering-and-dependency-rule) are enforced with oxlint's built-in `no-restricted-imports` rule. The web app uses oxlint's React and Next.js plugins instead of `eslint-config-next`.
- **Consequences:** One linter across the repo. The exact configuration is settled during implementation. If a rule that only ESLint has becomes necessary, ESLint can run next to oxlint with `eslint-plugin-oxlint`, which turns off the rules oxlint already checks. Record that in a new ADR.

## Verify at init

| Item | Fallback |
|---|---|
| Bucket policies work on the pinned RustFS version | Serve public images through a BFF route |
| Browser PUTs pass CORS with `RUSTFS_CORS_ALLOWED_ORIGINS` | `PutBucketCors`, then a streaming BFF route ([13 §9](./13-file-uploads.md#9-rustfs-and-deployment)) |
| RustFS rejects a PUT that differs from the signed size or type | The HEAD check at confirm remains the safety net |
| A presigned PUT that starts before expiry can finish after it on RustFS | Raise the TTL |
| RustFS honours `response-content-disposition` with UTF-8 file names | Sign `Content-Disposition` at upload time |
| The current `nestjs-i18n` release accepts NestJS 12 as a peer dependency | Small interceptor around `i18next`, same header and catalogues |
